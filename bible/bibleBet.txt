Rawwar ZBET BIBLE
Contesto di prodotto (cos'è RAWWAR)
• RAWWAR è un gioco di gambling battle‑royale con 8 giocatori virtuali. Ogni round dura
82–88s: 60s betting, 1s buffer, 14–20s playing (eliminazioni video), 7s results. Gira 24/7
in stanze parallele e indipendenti.
• Scommesse supportate (RTP 95.50%): WINNER 7.64, FTD 7.64, TOP2 27,
TOP3 53, EXACT2 55, EXACT3 335. Regola payout: stake × odds, con
maxWin per giurisdizione (default 3000.00).
• Provably fair: serverSeedHash pre‑bet → reveal post‑match; CSPRNG
HMAC_DRBG; shuffle Fisher–Yates.
• Roulette‑style settlement: prima mostriamo, poi regoliamo (show first, settle later).
Incomplete game: VOID tutti o SETTLE completo.
• Multi‑room: orchestrator assegna utenti alle stanze; ogni stanza ha il proprio engine e
websocket.
Missione di sviluppo (cosa dobbiamo costruire ORA)
• Implementare 5 servizi: Frontend, Orchestrator, Backend del Gioco, RGS mock, Casino
mock — tutti nello stesso codebase, differenze solo via config (Pre‑Prod ⇄ Prod).
• Consegnare contratti (REST/WS) vincolanti, catalogo errori completo con mapping a 6
messaggi UX, state machines, schema DB, sicurezza/compliance, test & CI/CD.
• Pre‑Prod (24h): SQLite, Redis single, 10 stanze, 56 video, e2e smoke. Prod 500k CCU:
Postgres HA, Redis Cluster, 560 video via CDN, mTLS, OTel, HPA.
Vincoli non negoziabili (da rispettare in revisione)
• Niente rename o aggiunte arbitrarie a: endpoint, eventi WS, payload, header richiesti,
**codici **`` e loro mapping → 6 messaggi UX.
• Pattern obbligatori: Repository/UnitOfWork, Outbox/Inbox, State Machine, Idempotency

• Compliance: GLI‑19 (designed‑to‑comply), RG (reality check configurabile + ACK), AML

§0.1 Identificatori (case‑sensitive)
• playerId — utente autenticato (REST, DB, RGS).
• playerIndex — indice concorrente (1..8) usato negli
eventi WS `match:*`.
Alias vincolante:
• CompetitorIndex = integer [1..8] (indice concorrente nei payload WS match:*)
• Obbligo: in /packages/shared-types esportare type CompetitorIndex = Branded<number,'CompetitorIndex'>.
• Nota: nei payload WS attuali il campo si chiama ancora "playerId" ma la semantica è CompetitorIndex; i client devono trattarlo come tale.
• roomId — stanza logica (namespace WS).
• matchId — round/partita in una stanza.
• roundId — identificatore round verso RGS.
• betId — scommessa singola.
• idempotencyKey — chiave idempotenza (POST/Batch).
• correlationId — tracciamento end‑to‑end.
§0.2 Phases (ordine e durata)
Engine: WAITING → BETTING(60s) → LOCK(1s max / 1000ms) → PLAYING(14–20s) →
RESULTS(7s) → SETTLEMENT.
Nota: Il TTL del lock Redis (SETNX+PEXPIRE) deve essere 1000ms.
Esposizione WS al FE: BETTING, PLAYING, RESULTS.

2) Pattern non‑negoziabili
• Repository + UnitOfWork: accesso DB transazionale; rollback ACID; una Unit per
richiesta.
• Outbox/Inbox: persist write + publish in transazione; consumer idempotente; DLQ con
retry policy esponenziale.
• State Machine (Backend del Gioco): WAITING → BETTING → LOCK →
PLAYING → RESULTS → SETTLEMENT.
• Circuit Breaker + Exponential Backoff (jittered): RGS/Casino; fallback; breaker
half‑open policy.
• DTO Validation (zod/typebox) su tutti ingressi (REST/WS). 400/error immediato.
• Correlation‑ID: header X-Correlation-Id e campo ws; obbligatorio in log, metrics,
traces.
• Rate limiting: per sessione (1 bet/2s), per IP (WAF/gateway), per endpoint.
• Clock sync: NTP/Chrony su nodi; server rifiuta skew > 60s con CLOCK_SKEW.
3) Domain model & regole di convalida
3.1 Entità
• Player { playerId, jurisdiction, limits }

3.2 Bet Types & Odds (RTP 95.50% certificato)
• WINNER 7.64:1 → selection=[p], p∈[1..8]
• FTD (First to Die) 7.64:1 → selection=[p], p∈[1..8]
• TOP2 27:1 → selection=[a,b] con a≠b, a,b∈[1..8]
• TOP3 53:1 → selection=[a,b,c] distinti
• EXACT2 55:1 → selection=[first,second] distinti
• EXACT3 335:1 → selection=[first,second,third] distinti
Convalida:
• valori distinti per array;
• range 1..8;
• EXACT* rispettano ordine;
• TOP* ordine irrilevante (normalizzare in sort crescente prima di persistenza).
Nota:
• L'RTP 95.50% è un target di compliance GLI-19 ma non vincolante in Pre-Prod.
• In Pre-Prod è ammesso RNG non certificato (es. Math.random).
• In Production l'RTP sarà garantito da RNG certificato di terza parte, con modello allegato GLI-19.
3.3 Rounding & payout
• payout = stake × odds, arrotondato a 2 decimali (banker’s) prima di credito.
• maxWin per giurisdizione (default 3000.00) → errore MAX_WIN_EXCEEDED.

8.2 Provably Fair (dettaglio implementativo)
• Pre‑bet: genera serverSeed (32 byte), persiste serverSeedHash =
SHA256(serverSeed).
• ClientSeed: hash cumulativo deterministico delle bet della stanza.
  Ordinamento e serializzazione canonica per clientSeed:
  • sortedBets = array delle bet ordinate per betId ASC (string compare UTF-8).
  • Serializzazione JSON canonica: chiavi in ordine stabile, nessuno spazio, UTF-8, nessuna virgola finale.
  • clientSeed = HEX(SHA256(JSON.stringify(sortedBets in formato canonico))).
  Qualsiasi altro ordine/serializzazione è NON valido ai fini dell'audit.
• CombinedSeed: SHA256(serverSeed || clientSeed || roomId ||
closeTsISO) (concatenazione byte con delimeter 0x1F).
• RNG: HMAC_DRBG(combinedSeed) → shuffle [1..8] con Fisher–Yates.
• Post‑match: rivela serverSeed; API di verifica restituisce serverSeed,
clientSeedHash, sequence e guida di verifica.
8.3 Bet processing & settlement
• Intake: PENDING fino a validazione RGS (batch a T‑0); idempotency su
Idempotency-Key.
• Close: lock atomico stanza (Redis SETNX chiave lock:room:
{roomId}:match:{matchId} TTL 1000ms (PEXPIRE)).
• Settlement: calcolo vincite; outbox eventi CREDIT batch; retry con backoff; rollback ACID
on failure; riconciliazione.

ammessi, facade UX mostrato, azioni FE obbligatorie, logging/metrics e retry/backoff.
22.0 Regole comuni (obbligatorie)
• Solo codici dal catalogo (§5.2 + Appendice D — Registry Errori). Qualsiasi altro codice
= errore CI.
• Envelope REST come in §4.2; **evento WS `error`** come in §4.3.
• UX shown: solo i 6 messaggi (§5.1). Mapping in /packages/shared-lib/
errors/facade.ts.
• Log: livello warn|error con code, correlationId, roomId, matchId,
playerId? (pseudonimizzato), durata richiesta.
• Metrics: counter errors_total{code=..., endpoint=...} e
histogram request_duration_seconds{...}.
• Retry policy: solo dove indicato (backoff esponenziale jittered). Nessun retry infinito.

24) Fallback e Safe‑guards
• RW-SYS-000 è l’unico fallback ammesso per eccezioni non classificate; alert S1 se
>0.5% negli ultimi 5m.
• Se un handler tenta di emettere un codice non registrato, lanciare RW-SYS-000 + log
critico con code_originale e bloccare il deploy via CI.
• FE non deve mai mostrare un RW-* direttamente all'utente: solo i 6 messaggi facade (§5.1).

Appendice D — Registry Errori
Appendice D rinvia a §23.1 come unica fonte canonica del Registry (REST + WS).
Schema DB logico (alto livello)
• Tabelle chiave: Users, Sessions, Bets, Matches, Ledger, AuditLogs
• Indici minimi: (matchId, createdAt) su Bets; (userId, createdAt) su Ledger
• Partizionamento: Bets/Matches per matchId

Testing Policy (vincolante)
• Coverage minima unit ≥80% (Assunzione se non approvata)
• Obbligatori: contract, integration, e2e, load, fault-injection
• Provably fair: includere vettore di test deterministico
  Esempio: serverSeed=base64("..."), clientSeed="abc", bets=[1,2,3], output atteso=[...]

Concurrency Strategy (vincolante)
• Lock policy: utilizzare distributed locks (Redis SETNX) con TTL fisso a 1000ms esclusivamente per close-round. Per bet placement usare idempotency keys (48h TTL) senza lock.
Commento Claude: Lock policy chiarita - lock solo per close-round, idempotency per placement.
• Race risolta da timestamp server: primo evento valido, successivi = already-applied
• Meccanismi: Idempotency 48h, Single Active Session, rate limit 1/2s

Failure Recovery & Compensating Actions
• Circuit Breaker con exponential backoff (Assunzione: 3 tentativi, jitter ±50%, cap 2s)
• Retry solo su errori temporanei (rete/timeouts), mai su 4xx di validazione
• Compensazione ledger: in caso di addebito parziale fallito, applicare "compensating transaction" con correlationId
• RPO ≤ 5 minuti, RTO ≤ 15 minuti (vincolante, vedi §14)

API Versioning & Deprecation (vincolante)
• SemVer; path /api/v{MAJOR}; WS subprotocol {product}.v{MAJOR}
• Nessun breaking in MINOR/PATCH; breaking solo in MAJOR
• Header Deprecation/Sunset obbligatori
• Supporto MAJOR per 12 mesi (Assunzione se non approvato)

Admin/Backoffice endpoints — vincoli
• /void ammesso solo in fasi WAITING/RESULTS
• Audit obbligatorio per ogni void/drain
• Esempio: { status:"VOIDED", matchId:"m1" }

Pre-Production Gate (vincolante)
• Criteri di ingresso: contract test 100% verdi, e2e smoke test, DR test minimo
• Exit criteria: rollback validato, deploy canary 10%
• Metriche quantitative: contract test 100%, smoke test coverage 80%

Production Readiness 500k CCU (vincolante)
• Criteri di superamento: load test 30m, p95 <200ms, error-rate <1%
• Headroom ≥20%
• Runbook di rollback pronto
